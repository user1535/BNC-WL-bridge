# WorldLand xWL ↔ BSC wWL 개발계획서

2026-11-05 개정. WorldLand에서 WL을 소각해 xWL을 발행하고, WL과 xWL은 같은 체인에서 당사자끼리 거래한다. BSC로 옮기는 자산은 xWL이며, 기존 V2의 양방향 소각·발행 흐름을 연결한다.

## 1. 자산 흐름과 개발 범위

| 경로 | 가격·수량 | 체결 방법 |
| --- | --- | --- |
| **WL 소각 → xWL 최초 발행** | 소각량과 발행량이 1:1 | WorldLand 계약에서 사용자가 보낸 WL을 소각하고 동일 수량의 xWL을 발행 |
| **WL ↔ xWL 직접 거래** | 거래 당사자 합의 가격 | 같은 WorldLand 체인에서 WL 전송과 xWL 전송을 각각 지갑에서 서명 |
| **xWL ↔ wWL 브리지** | 양방향 1:1 | 출발 ERC20을 소각한 뒤 증명하고 목적지 ERC20을 동일 수량으로 발행 |

예를 들어 WL 10개를 소각해 xWL 10개를 발행하고 BSC로 옮기면 wWL 10개를 받는다. wWL 10개를 WorldLand로 반환하면 xWL 10개를 받는다. 이후 매수자가 10 xWL에 8 WL을 제시하면 두 사람이 그 조건으로 직접 거래할 수 있다. 직접 거래에서 받은 WL은 매수자가 보유하던 자산이다.

### 1.1 기존 구현의 재사용 범위

기존 로컬 V2에서 두 ERC20의 양방향 소각·발행, 사용자의 지갑 서명, 실제 RISC Zero composite receipt 생성·서버 SDK 검증, 중복 청구 차단과 재시작 복구를 검증했다. 이번 작업은 검증한 경로에 새 xWL·wWL 주소를 연결하고 WL 소각 발행과 같은 체인 전송을 추가 검증하는 것이다. [V2 실행 및 ABI](burn-mint-runtime.md) · [V2 검증 기록](burn-mint-checklist.md)

## 2. 구현 설계

### 2.1 WL 소각과 xWL 최초 발행

사용자가 WL 수량과 xWL 수신자를 선택하고 지갑에서 네이티브 WL을 첨부한 발행 거래를 서명한다. WorldLand 계약은 실제 첨부된 WL을 합의된 소각 경로로 보내고, 같은 수량의 xWL을 발행한다. 가스비는 별도로 처리한다. 소각·발행·이벤트 기록은 하나의 거래에서 함께 반영한다.

- 0 수량, 잘못된 수신자, 정확히 환산할 수 없는 단위는 거부한다. 어느 단계든 실패하면 소각과 발행을 함께 되돌린다.
- 진입 발행량은 실제 소각량에서만 산출한다. 지급량, 수신자, 발행량과 누계를 조회할 수 있게 한다.
- 기존 전송 규칙으로 회수 경로가 없는 주소에 보낼 수 있는지 WL 측과 확인한다. 이 방식은 유통에서 WL을 제외한다. 프로토콜 공급량 차감과의 차이는 탐색기·공급량 집계에 명시한다.
- 소각 주소나 방식, xWL 단위와 초기 공급, 진입 발행 한도는 배포 설정을 확정하기 전에 합의한다.

### 2.2 WorldLand의 WL·xWL 직접 거래

초기 범위는 지갑의 일반 전송을 이용한 직접 거래다. 매도자가 상대 주소로 ERC20 xWL을 보내고, 매수자는 합의한 수량의 네이티브 WL을 매도자에게 보낸다. 양쪽 거래는 각각 서명하며 가격은 당사자가 정한다.

두 전송은 독립적으로 확정된다. 선송금한 쪽은 상대가 지급하지 않으면 체인에서 반대편 자산을 자동으로 받을 수 없으므로, 이 경로는 상대방을 신뢰하는 거래에 적합하다. 상태 확인도 양쪽 거래 해시와 실제 수신량을 기준으로 한다.

서로 모르는 상대와의 거래가 필요해지면 두 지급을 한 트랜잭션에서 실행하는 원자적 교환 계약을 후속으로 검토한다. DEX, 유동성 풀, 주문서와 시세 견적은 운영 수요에 따라 별도로 검토하는 확장 항목이다.

### 2.3 xWL ↔ wWL V2 브리지 연결

WorldLand에서는 xWL, BSC에서는 wWL을 브리지 자산으로 고정한다. 기존 V2 ABI와 증명 입력 형식을 사용할 수 있는지 확인하고, 새 토큰 주소와 상대 체인·receiver를 배포 설정에 연결한다. 방향별 입력은 해당 출발 체인의 ERC20 소각 이벤트다.

1. 사용자가 지갑에서 출발 ERC20을 소각하고 목적지 수신자를 지정한다.
2. 운영자는 확인 블록 수를 충족한 원본 블록의 receipt root를 등록한다. 서버는 receipt/MPT와 이벤트 증거를 생성하고 실제 RISC Zero composite receipt를 SDK로 검증한다.
3. 사용자가 목적지 청구를 서명한다. 목적지 계약은 등록 루트에 대한 MPT, 지정 emitter, 이벤트·자산 도메인·수량·수신자와 소각 ID의 중복 여부를 검증하고, 같은 수량을 1회 발행한다.
4. 소각은 성공했지만 목적지 발행이 남으면 같은 소각 ID로 상태를 조회해 재개한다. 발행·처리 ID·누계의 갱신은 한 거래에서 이루어진다.

서버와 RPC는 신뢰 대상으로 두고, 서버 SDK가 RISC Zero 증명을 검증한다. 목적지 계약의 검증 기준은 운영자가 등록한 루트이며, 합의·최종성은 독립적으로 인증하지 않는다. 양쪽 사용자는 거래를 직접 서명한다.

새 토큰 주소가 포함된 소각 이벤트와 증명은 새 배포의 도메인에 속한다. 이전 배포의 증거는 이전 계약에 연결한다. 입력 형식이나 guest가 바뀔 때는 정책과 Image ID를 고정한 후 재검증한다.

### 2.4 단계와 완료 조건

| 단계 | 작업 | 완료 기준 |
| --- | --- | --- |
| 1. 환경·소각 방식 확정 | WL 팀과 RPC, receipt 데이터, 소각 방식과 단위·초기 공급 설정을 확인 | 조회 가능한 블록·receipt 예시와 소각 처리·집계 방식이 명시됨 |
| 2. 1:1 진입 구현 | 새 로컬 세션에서 WL 소각과 xWL 발행을 연결 | 10 WL 소각에 10 xWL 발행. 소각 또는 발행 실패 시 전체 원상복구. 무소각 발행 거부 |
| 3. 같은 체인 전송 확인 | 두 계정이 가격을 정해 xWL과 WL을 각자 직접 전송 | 두 영수증에서 합의한 수량과 수신자 확인. 한 건만 확정된 경우를 거래 완료로 표시하지 않음 |
| 4. 기존 V2 연동 | 새 xWL·wWL 주소로 양방향 소각·증명·청구 수행 | 양방향 실제 receipt의 SDK 검증과 지갑 청구 성공. 잘못된 체인·주소·수량·수신자 및 중복 소각 ID 청구 거부 |
| 5. 왕복·복구 확인 | WL 소각 → xWL → wWL → xWL → 같은 체인 직접 거래를 실행 | 최초 발행·브리지 소각·목적지 발행의 수량 일치. 대기 중인 청구를 재시작 후 동일 ID로 재개 |

로컬 검증은 chain ID 31337/31338의 새 격리 세션에서 수행한다. 기존 V1·V2 세션과 실제 receipt는 회귀 검증 근거로 보존한다. 새 proving이 필요한 단계에서는 활성 작업과 lock을 먼저 확인하고 CPU 최대 12개, 가용/cgroup 메모리 70%, 1,800초, 파일당 64 MiB 제한을 적용한다.

## 3. WL 측 확인 항목과 운영 기록

- **증명 데이터.** 블록 번호·해시·receiptsRoot, 거래 순서, 전체 영수증과 xWL 소각 로그를 조회할 수 있는 RPC 또는 explorer API를 확인한다.
- **소각 경로.** 네이티브 WL을 유통에서 제외하는 방식과 확인 가능한 영수증·장부 표시를 합의한다.
- **ERC20과 지갑.** xWL을 배포할 환경과 주소를 정하고 같은 체인에서 일반 WL 전송과 xWL 전송이 가능한 지갑 경로를 확인한다.

WL 소각을 통한 xWL 진입 발행 누계와 브리지 소각·발행 누계를 분리한다. 미발행량은 방향별 소각 누계에서 상대 체인 발행 누계를 빼서 집계하고, 정확한 완료 여부는 소각 ID를 기준으로 판단한다. 일반 WL·xWL 전송은 브리지 소각·발행 누계에 반영하지 않는다.
